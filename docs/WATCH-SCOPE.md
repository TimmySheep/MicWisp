> 归属 **iOS/iPadOS 线**（同一 Xcode 工程、同一 App bundle，所以同许可 = MIT），
> 但**文件边界独立**。
>

## 1. 功能清单（**全部要实现**）

| ID | 功能 | 说明 | 依赖 |
|---|---|---|---|
| **W-1** | **远程麦克风开关** | 手表上切换 iPhone 端麦克风开/关。核心场景：临时静音不必掏手机 | 无 |
| **W-2** | **连接状态显示** | 显示 iPhone ↔ 上游机器（Windows/macOS）的连接状态、机器名、已持续时长 | 无 |
| **W-3** | **表盘复杂功能** | 把连接与静音状态放到**表盘 / Smart Stack**，抬腕即见，**不必打开 App** | 无 |
| **W-4** | **震动确认** | 静音/恢复等操作成功或失败时，用手腕震动给反馈，**不必看屏幕** | 无 |
| **W-5** | **断连震动告警** | 与上游断开、或延迟飙升时，**震动手腕报警** | 无 |
| **W-6** | **静音提醒（绝不自动恢复）** | 静音中周期性轻震提醒你"仍在静音"，避免忘了开回来 | 无 |
| **W-7** | **数码表冠调增益** | 用 Digital Crown 调输入增益，不必掏手机 | **依赖上游控制通道补丁** |

### 为什么 W-6 是"提醒"而不是"定时自动恢复"

用户**明确否决**了"静音 2 分钟后自动恢复"的原始设计，理由正确且重要：

> 自动恢复会在**用户不知情的情况下打开麦克风**，构成**隐私风险**。

W-6 保留了原本要解决的问题（"忘了开回来"），但**把决定权留给用户**：
只震动提醒，**是否恢复必须由用户显式操作**。见第 2 节安全红线。

### 明确不做（防止以后被"功能列表"诱惑）

- ❌ 手表独立采集音频 —— 硬约束（麦克风在 iPhone 上）
- ❌ 手表直连上游机器 —— watchOS 网络限制
- ❌ 频谱 / 波形显示 —— 屏幕太小且耗电
- ❌ 在手表上选设备 / 改复杂配置 —— 屏小做不好，iPhone 更合适
- ❌ 在手表上看 / 管理录音文件 —— 不是手表的活
- ❌ **任何自动改变麦克风状态的行为** —— 见第 2 节（安全红线）

## 2. 安全红线（**不可协商，优先级高于所有功能**）

### 2.1 禁止自动改变麦克风状态

> **麦克风的开关只能由用户的显式操作触发。任何"到点自动开麦/自动恢复"的设计一律禁止。**

**起因**：曾设计"静音定时自动恢复"，用户否决——**自动恢复 = 在用户不知情时打开麦克风 = 隐私事故**。

**允许**：提醒（震动 / 通知 / 表盘状态）。
**禁止**：自动恢复、自动取消静音、任何"到点自动开麦"。
**推论**：若将来要做"自动"特性，只能是**自动变得更安全**（如自动静音），
**绝不能是自动变得更能采集**。

### 2.2 状态显示不得撒谎

手表显示"已连接/未静音"必须是**真实状态**。拿不到真实状态时，
显示**未知 / 最后已知 + 时间**，不得沿用乐观的旧值。

### 2.3 失败必须显式可见

指令失败（断连、超时、被拒）时，手表**必须明确显示失败**，不得静默吞掉。
配合 W-4 的失败震动。

## 3. 架构（唯一可行方案，不要试图绕过）

```
   Apple Watch  ── WCSession ──▶  iPhone  ── MicYou 协议 TCP 8554 ──▶  上游机器
  (MicWisp Watch)                 (MicWisp iOS)                      (Windows/macOS)
```

### 3.1 为什么手表不直连上游机器

1. **麦克风在 iPhone 上** —— 要控制与转发的是 iPhone 的音频链路
2. **watchOS 严格限制网络** —— 手表 App 默认不许长期持有网络连接（省电），
   连接会被系统周期性回收
3. **连接状态的"真相"在 iPhone 端** —— iPhone 才是与上游建连的一方

**结论：手表只跟 iPhone 说话。** 不要自作聪明。

### 3.2 通信通道选择（已按 Apple 官方文档核实，**不要自行更改**）

两侧的"可达性"是**不对称**的，方向决定通道：

| 方向 | 可达性（Apple 官方表述） | 应使用 |
|---|---|---|
| **watch → iPhone** | **iPhone app 永远被视为可达**；从手表调用会**唤醒后台的 iPhone app** | `sendMessage` |
| **iPhone → watch** | 手表 app **仅在其运行（前台）时**才算可达 | `updateApplicationContext` |

Apple 原文：
> "The iOS app is always considered reachable, and calling this method from your
> Watch app wakes up the iOS app in the background as needed."

**因此**：

- **W-1（指令）用 `sendMessage`** —— iPhone 永远可达 → **静音指令可靠送达**
- **W-2 / W-3（状态）用 `updateApplicationContext`** —— "最新值覆盖"语义，
  正好匹配状态显示；手表醒来即拿到最新快照
- **W-5 / W-6（告警与提醒）** —— 告警尽可能即时：前台叠加 `sendMessage`，
  失败回退 `updateApplicationContext`；提醒类可用本地通知/震动，不依赖网络
- **W-7（增益）用 `sendMessage`** —— 与 W-1 同方向，但需先有上游控制通道

红线：
- **不要**用 `updateApplicationContext` 传指令（会被覆盖丢失）
- **不要**用 `sendMessage` 传状态（手表不在前台就丢）

## 4. 消息契约（**必须版本化**，两侧共用一份类型定义）

**状态快照（iPhone → 手表）**

```json
{
  "v": 1,
  "micEnabled": true,
  "connection": "connected",
  "peerName": "TIM-PC",
  "since": 1759900000,
  "gain": 0.75
}
```

- `connection` ∈ {`disconnected`, `connecting`, `connected`, `error`}
- `since`：进入该状态的时间戳（用于显示"已连接 12 分钟"）
- `gain`：输入增益 0.0–1.0（W-7 用；不支持时省略）
- 手表离开范围时：保留最后已知快照并**标注时间**，不得假装实时

**指令（手表 → iPhone）**

```json
{ "v": 1, "cmd": "setMic",  "enabled": false, "reqId": "<uuid>" }
{ "v": 1, "cmd": "toggleMic",                 "reqId": "<uuid>" }
{ "v": 1, "cmd": "setGain", "gain": 0.75,     "reqId": "<uuid>" }
```

- `reqId` 必须**在回执里带回**，用于配对与失败提示
- 两侧都要校验 `v`；不认识的版本**拒绝并回复错误，不要猜**

**回执（iPhone → 手表）**

```json
{ "v": 1, "reqId": "<uuid>", "ok": true }
{ "v": 1, "reqId": "<uuid>", "ok": false, "error": "notConnected" }
```

## 5. 生命周期与必须处理的坑（已核实）

1. **`WCSession.isSupported()` 在 iPad 上返回 `false`** —— 不检查会崩。
   MicWisp 是 iPhone+iPad 通用 App，**必须先判断**再访问 `WCSession.default`
2. **`WCSession.delegate` 必须在 `activate()` 之前设置**，且在 App 启动早期完成
   （SwiftUI 里在 `@main App` 创建的 manager 中完成，不要放在某个 View 的 `onAppear`）
3. **`sessionDidDeactivate` 里必须重新 `activate()`** —— 用户换手表后不重新激活
   会静默失效
4. **委托回调在后台线程** —— 更新 UI 必须跳回主 actor（`Task { @MainActor in ... }`）
5. **`isReachable == true` 也可能失败**（手表 app 不在前台）——
   错误处理必须实现，不可依赖
6. **手表后台不会常驻** —— 长时间未激活会被系统卸载；
   再次打开时 `applicationContext` 会到，`sendMessage` 不会。**状态设计要容忍这点**

## 7. 验收标准（**逐条实测，不许口头声称通过**）

**通用**
- [ ] iOS app 与 Watch app **都能构建**（`xcodebuild` 双 target）
- [ ] **iPad 上不崩**（`isSupported()` 分支正确）

**W-1 远程麦克风开关**
- [ ] iPhone app 在**后台**时，手表切换 → iPhone 端麦克风状态**确实变了**（真机）
- [ ] 静音后**音频流行为明确**（停止发送音频或发静音），且**会话不断开**
- [ ] 失败时**明确显示失败**（配合 W-4 震动）

**W-2 连接状态**
- [ ] 上游未启动 → 显示 `disconnected`
- [ ] 连上上游 → 显示 `connected` + 正确机器名
- [ ] 断开网络/上游 → 状态**跟着变**
- [ ] 手表离开范围再回来 → 显示**最新**状态，非陈旧值

**W-3 表盘复杂功能**
- [ ] 表盘上可见连接与静音状态（至少一种系统表盘样式渲染正确）
- [ ] 状态变化后表盘在系统允许的时间线内更新
- [ ] 无数据时显示未知态，不显示错误或空白崩溃

**W-4 震动确认**
- [ ] 操作成功与失败**震动可区分**（成功一种、失败另一种）
- [ ] 手表静音模式下也能被感知（不依赖声音）

**W-5 断连震动告警**
- [ ] 与上游断开时**确实震动手腕**
- [ ] 恢复连接时不误报
- [ ] 不产生告警风暴（需去重/节流）

**W-6 静音提醒（关键：不得自动恢复）**
- [ ] 静音持续期间能**周期性提醒**（震动/通知）
- [ ] **绝不自动取消静音** —— 必须人工点按才恢复
- [ ] 恢复操作需用户显式确认路径清晰

**W-7 数码表冠调增益**
- [ ] 表冠旋钮能改变增益，iPhone 端与上游**确实生效**
- [ ] 仅在**上游控制通道补丁可用**时启用；不可用时**隐藏或禁用**，不得假装可用

**必须如实标注的不可验证项**
- ⚠️ **模拟器不能复现后台/唤醒行为**（Apple 明确说明）。
  模拟器只用于 UI 与编译验证；**后台唤醒、真实静音、震动、表盘刷新必须真机**。
- ⚠️ 若因签名/设备限制无法真机验证，**必须如实标注"未真机验证"**，不得写成通过。
