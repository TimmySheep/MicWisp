# 路线 B 的工作范围界定

> 目的：明确"只写原生 UI"这个说法准确到什么程度，以及实际工作量。

## 1. 结论：方向对，但有两处修正

**对的部分**：核心（传输/协议/DSP/虚拟音频设备）完全复用上游，你只写各平台原生 UI。
Mac 一套、Windows 一套——**是的，两套独立 UI 代码**（原生意味着不能共享 UI 代码）。

**修正 1：不只是 UI，还有一层"集成"**
你的 UI 需要驱动无头 CLI，但**目前这个控制通道不存在**：
- `micyou-cli serve` 的事件是**人类可读文本行**（`[mic] connected: ...`、`[stats] latency ...`），
  不是结构化输出。
- 因此需要二选一：
  - **给 CLI 加 JSON 事件模式**（小补丁、增量、适合提上游 PR）— 推荐
  - 解析文本行 — 脆弱，不推荐

**修正 2：两套 UI = UI 工作量 ×2**，无法通过"共享 UI 代码"规避。

## 2. 现有 UI 的真实规模（实测）

| 指标 | 值 |
|---|---|
| 文件数 | 80（`.vue` + `.ts`） |
| 总行数 | **10,551** |

功能面（不只是"一个连接按钮"）：

- 设置：音频（297）、关于（292）、外观（278）、通用（253）、设置窗口（288）
- 主题目录（270）
- 引导向导（253）
- 袖珍模式布局（258）
- 音频：均衡器（239）、音频链（211）、监听（179）
- i18n（简/繁/英三语）

## 3. 可行的工作量切分

| 范围 | 估算 | 说明 |
|---|---|---|
| **MVP** | 1.5–3k 行/平台 | 连接（Wi-Fi/USB/Web）+ 设备发现 + 状态与电平 + 基础设置 + 菜单栏/托盘 + 自启 |
| **接近对齐** | ~10k 行/平台 | 含插件市场、主题、EQ、音频链、引导、三语 i18n |

**MVP 明显可控；全功能对齐不是小工程。** 建议先做 MVP。

## 4. 建议顺序

1. **macOS MVP 先行**（与既定"Mac 优先"一致）
2. DSP 等高级设置**先用 `server.json` 手工配置**，UI 后补——避免一开始就做庞大的设置界面
3. Windows 版在 macOS 版稳定后启动
4. 插件系统可整体后置（占现有 UI 的约 2000 行）

## 5. 待确认（影响 UI 交互设计）

1. **CLI 是否支持运行时改配置**，还是必须重启服务才能生效？
   （`serve.rs` 的启动参数为 port/mode/device/bind；`commands.rs` 有 settings 的 JSON 读写，
   但运行中的服务是否热加载尚未核实。）
2. `mode_lock`（`RunMode::Cli` / `RunMode::Gui`）意味着 GUI 与 CLI 互斥运行。
   你只发 CLI 没问题，但**不能同时开着官方 GUI 和你的后端**。
3. 事件类型的完整清单（需读 `micyou_core::events::ServerEvents` 全部 trait 方法），
   才能定义 JSON 事件模式。

## 6. 一句话

**"只写一套原生 UI"在 MVP 范围内成立；但别忘了那条薄薄的集成层（CLI 结构化输出），
以及 Windows 是第二套完整实现。**
